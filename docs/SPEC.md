# gatecost — Specification

Status: Draft
Language: Python (standard library only)

## 1. Overview

`gatecost` estimates the logic-gate cost of an RTL (HDL) design and, above all, the **cost delta introduced by a modification** to it. It is designed primarily to be invoked by an AI agent as a skill, so that the agent can answer, within seconds and without any external EDA tool, the question:

> "What does this RTL change cost, in gates?"

The tool is a fast, explainable estimator. It does not perform logic synthesis. Every result carries an explicit confidence level so that the caller knows how far the figure can be trusted.

## 2. Goals

| ID | Goal |
|----|------|
| G1 | Report the gate-equivalent (GE) delta between two states of an RTL design, in total, per module, and per source line. |
| G2 | Run in well under one second on typical designs; no daemon, no heavy elaboration. |
| G3 | Produce output that is directly consumable by an LLM agent: stable JSON and a compact, token-efficient text form. |
| G4 | Be honest about uncertainty: every figure has a range and a confidence level; unsupported constructs are reported, never silently ignored. |
| G5 | Depend on nothing but the Python standard library. No Yosys, no synthesis tool, no compiled extension. |
| G6 | Work with zero configuration in the common case; allow explicit configuration when needed. |
| G7 | Let the caller estimate the cost of a hypothetical construct before writing it. |
| G8 | Be adoptable as a git submodule dropped into any agent's skills directory (`.claude/skills/`, `.github/skills/`, `.opencode/skills/`, ...) with no installation step and no write access to its own directory. |

## 3. Non-goals

- Replacing logic synthesis, place-and-route, or sign-off area/timing reports.
- Timing, power, or routability analysis.
- Functional verification, linting, or equivalence checking.
- Simulation of any kind.
- Supporting non-synthesizable HDL (testbenches, delays, file I/O, classes).

## 4. Users and Usage Model

**Primary user: an AI agent** executing `gatecost` through a shell. The agent edits RTL files in a working tree, then asks for the cost of what it changed.

**Secondary users:** engineers using the CLI or the Python API, and CI jobs enforcing area budgets.

Typical agent workflow:

```
... agent edits RTL in a git working tree ...
gatecost diff                     # cost of the change against HEAD
```

Outside git, the agent runs `gatecost snapshot` before editing and `gatecost diff --since-snapshot` afterwards. To weigh options before writing code, it runs `gatecost estimate`.

## 5. Architecture

```
 sources ──► Lexer/Parser ──► Elaborator ──► Word-level IR ──► Cost Model ──► Cost Tree
                                                                                  │
 baseline ─► (same pipeline) ───────────────────────────────────────────► Differ ─┴─► Reporters
```

Each stage is a pure function of its inputs, which makes results deterministic and cacheable.

### 5.1 Front-end

There is one front-end per hardware description language, all producing the same language-neutral IR. Files are routed by extension: `.v`, `.vh`, `.sv`, `.svh` to the Verilog/SystemVerilog front-end and `.vhd`, `.vhdl` to the VHDL front-end. Mixed-language designs are supported: an instance in one language may refer to a module or entity in the other.

Common properties, detailed in [`docs/FRONTEND.md`](FRONTEND.md) (normative):

- Hand-written lexer and recursive-descent / Pratt parser per language, using only the standard library.
- **Error-tolerant**: a parse error in one construct, module, or entity does not abort the analysis; the affected region is recorded as a diagnostic and the remainder is analyzed.
- **Degradation ladder** for every construct: exact, approximated with a recorded assumption, or skipped with a diagnostic. Skipping a construct in the changed cone lowers the confidence.
- Verilog/SystemVerilog: a full preprocessor (`` `define``, conditionals, `` `include``, macros with arguments) with a line map back to the original source.
- VHDL: a built-in model of the standard IEEE packages (`std_logic_1164`, `numeric_std`, `numeric_std_unsigned`, the legacy `std_logic_arith` family, `math_real`, `fixed_pkg`, `float_pkg`) and a lightweight type-directed operator resolution; no external library sources are required.
- Every AST and IR node retains its source location (file, line, column), including code generated by macro expansion.

### 5.2 Elaboration

Elaboration is demand-driven and common to both languages in structure (details in `docs/FRONTEND.md`):

- Parameter / generic resolution, including overrides at instantiation, with constant-expression evaluation (including constant functions).
- `generate` unrolling and loop unrolling in procedural code, all bounded by configurable limits.
- Type, width, and signedness inference following each language's rules.
- Conversion of procedural code (always blocks, processes) to dataflow by symbolic execution, with recognition of registers, resets, enables, latches, and memories.
- Hierarchy construction with sharing of identical `(module, parameters, constant ports)` elaborations, and instance counts.
- Top-module auto-detection (the unit not instantiated by any other) with explicit override.

### 5.3 Word-level IR

The IR is a language-neutral word-level netlist with bit-level facts. Its normative specification (nets and signal specifications, node catalogue, builder and local simplification rules, analysis passes, canonical keys, hierarchy, limits) is [`docs/IR.md`](IR.md). Summary of the operations:

| Category | Operations |
|----------|------------|
| Arithmetic | `ADD`, `SUB`, `NEG`, `MUL`, `DIV`, `MOD`, `SHL`, `SHR`, `SAR`, `POW` (constant exponent) |
| Logic | `AND`, `OR`, `XOR`, `XNOR`, `NOT`, reduction operators |
| Comparison | `EQ`, `NE`, `LT`, `LE`, `GT`, `GE` |
| Selection | `MUX`, `PMUX` (parallel mux), `DECODE`, `PRIORITY` |
| Wiring | slice, concat, replicate, constant (zero cost) |
| State | `DFF` (with sync/async reset, enable), `LATCH` |
| Memory | `MEM` (depth, width, read/write ports), `ROM` |
| Hierarchy | instance of a module or a black box |

Principal IR requirements (needed by §5.4):

- Each net carries a known-bit mask and value, signedness (with sign-replication tracking), a demanded-bit range, and a fanout count.
- Operations are hash-consed at construction (structural hashing).
- `MUX`/`PMUX` nodes carry an exclusive-branch group tag identifying trees built from a single `if`/`case`/`?:`.
- Additional operations: `SUM` (fused datapath cluster), `ENCODE`, and `ROM` (retaining its contents).
- Registers carry the reset kind, whether the reset value is constant, the enable, and a flag marking a recognized enable feedback.
- Memories carry the read style (synchronous or asynchronous) and port counts.

The IR performs light structural simplification only: constant folding, demanded-bit trimming, removal of unused logic, structural hashing, and recognition of enable and reset patterns on registers. No logic optimization beyond that.

### 5.4 Cost model

A cost model maps each IR operation to an area in **gate equivalents** (1 GE = area of a 2-input NAND) as a function of operation type, operand widths, and constant operands. The full formulas, primitive table, profile format, and test requirements are specified in [`docs/COST_MODEL.md`](COST_MODEL.md), which is normative. The principles are:

- **Primitive-based.** Every formula is expressed in library primitives (NAND2, XOR2, MUX2, FA, DFF, ...), whose GE values come from the active profile. Overriding a primitive propagates to every operation using it.
- **Consistent scenarios.** Each operation is evaluated under three scenarios: `min` (smallest plausible architecture), `typ` (the profile's architecture policy at moderate timing), and `max` (fastest architecture with a sizing factor). Scenarios are internally consistent, not independent bounds.
- **Deltas per scenario.** A delta is computed as `after_s − before_s` within each scenario, never as `max(after) − min(before)`. Operations that are unchanged cancel exactly. Independent residual error (a fixed per-quality-class constant) is added in quadrature over changed operations only, and combined in quadrature with the scenario spread to form the range (`COST_MODEL.md` §5.1). The residual of an operation matched before and after is correlated and only covers the part that changes.
- **Avoid over-estimation.** Costing is preceded by linear-time reductions that reproduce the obvious gains of synthesis: bit-level constant propagation, demanded-bit trimming, dead and duplicate logic removal, datapath fusion, resource sharing across mutually exclusive branches, enable recognition, and constant-port propagation. A general logic optimizer is out of scope.
- **Quality classes.** Each operation class is marked `good`, `medium`, or `poor` (for example, dividers, ROMs, and memories are `poor`). The class feeds the confidence level (§9.1).
- **Deterministic arithmetic.** Costs are integer milli-GE and are rounded only at output.
- **Data-driven profiles.** A profile (TOML) declares primitive GE values, architecture and timing policy, memory-macro parameters, and black-box costs; it may extend another profile. The tool needs no calibration, reference data, or setup to run: built-in profiles work out of the box. The built-in `generic-asic` profile is calibrated on one reference point (Yosys + Nangate 45 nm, no timing constraint; `COST_MODEL.md` §5.3), not on a commercial flow.

### 5.5 Cost tree

The result of costing a design is a tree: design → module instance → operation. Each operation node carries the three scenario values and its residual uncertainty, its category and quality class, its source location (including the macro definition site for macro-generated code), the formula and architecture chosen, declared and effective (post-folding) widths, assumption tags (`shared`, `fused`, `const_folded`, `macro`), a primitive breakdown (for example `{"FA": 31, "HA": 1}`), a matching key (named and structural), and the provenance facts (parameters, constants, widths) that determined its cost. Savings from sharing, fusion, and folding are assigned to the surviving operation, so the design total is exactly the sum of its operation costs, weighted by instance counts.

### 5.6 Differ

The differ compares two cost trees and explains the difference. Its normative specification is [`docs/DIFF.md`](DIFF.md). In summary:

- **Exact additivity.** The sum of all contributor deltas equals the total delta in every scenario; every view (per module, per line, per cause, per category) sums to the same total.
- **Stable matching.** Modules are matched by name (independently of the file), instances by hierarchical path, and operations through successive tiers: a name-sensitive key, a rename-tolerant structural hash, and a line alignment of the two sources. A module whose canonical cost tree is unchanged contributes exactly zero, so reformatting, comments, renames, file moves, and declaration reordering yield no delta.
- **Intrinsic versus multiplicity.** For a module instantiated several times, the delta splits into a change of the module body (valued at the current instance count) and a change of the instance count (valued at the previous per-instance cost).
- **Cause analysis.** Every contributor has a reason from a closed set (`added`, `removed`, `width`, `constant`, `parameter`, `structure`, `architecture`, `sharing`, `fusion`, `register`, `multiplicity`, `blackbox`). Changes propagated from a modified parameter or constant are traced to the changed line and grouped under it, so that one edit yields one explained contributor instead of many unrelated ones.
- **Per-scenario deltas** with the uncertainty rules of `docs/COST_MODEL.md` §5.
- **Verdicts:** `NO_CHANGE`, `NEGLIGIBLE`, `INCREASE`, `DECREASE`, `UNCERTAIN`, `NOT_COMPARABLE`.
- **Scoped work.** Only changed modules and their instance paths are traversed.

### 5.7 Reporters

| Format | Purpose |
|--------|---------|
| `agent` | Compact ASCII text for LLM consumption (see §8.1) |
| `json` | Full machine-readable result with a stable, documented schema (see §9) |
| `text` | Human-readable table |
| `markdown` | Suitable for pull-request comments |

All formats are rendered from one internal result object. Their normative specification is [`docs/OUTPUT.md`](OUTPUT.md).

## 6. Supported Languages

| Language | Coverage |
|----------|----------|
| Verilog-2005 | Synthesizable subset |
| SystemVerilog | Synthesizable subset: `logic`, `always_ff`/`always_comb`/`always_latch`, packed structs and unions, `enum`, `typedef`, packages, `generate`, functions, basic interfaces and modports |
| VHDL-93 and VHDL-2008 | Synthesizable subset: entities, architectures, processes, `generate`, packages, records, enumerations, `numeric_std` and legacy IEEE arithmetic packages |

Each construct is classified as *exact*, *approximated*, or *skipped*; the full support matrices are in `docs/FRONTEND.md` (§3 for Verilog/SystemVerilog, §10.5 for VHDL). Non-synthesizable code (testbench constructs, delays, assertions, file I/O, classes, access types) is ignored without effect on the estimate. Constructs whose cost cannot be derived statically (for example, unbounded loops or unresolved overloads) are reported as diagnostics with a partial result.

Instantiated units that are not defined in the sources (library cells, vendor primitives, missing files) are black boxes: costed through the profile if listed there, and otherwise reported as unknown with a zero contribution plus a diagnostic.

## 7. Inputs and Baseline Selection

The analyzed project is the **host project** (the project in which the tool is invoked), never the tool's own directory. Project root and source discovery, and the list of excluded directories, are specified in [`docs/DISTRIBUTION.md`](DISTRIBUTION.md) §4.

Source selection, in order of precedence:
1. Explicit paths on the command line.
2. A `gatecost.toml` project file (see §10).
3. Auto-discovery of `*.v`, `*.sv`, `*.vh`, `*.svh`, `*.vhd`, `*.vhdl` under the project root, and of filelists (`*.f`), excluding the tool's own directory, `.git`, `.gatecost`, skills directories, and common build and vendor directories.

The "before" state of a comparison, in order of precedence:

| Mode | Command | Notes |
|------|---------|-------|
| Git reference | `gatecost diff --base-ref <ref>` (`merge-base` is accepted as shorthand for the merge base with the default branch) | Reads blobs through the `git` executable when available; this is the only optional interaction with an external program. |
| Snapshot | `gatecost snapshot` then `gatecost diff --since-snapshot` | Stores a copy of the relevant sources under `.gatecost/`. No external program required. |
| Directories | `gatecost diff --before <dir_a> --after <dir_b>` | Compares two source trees. |
| Default | `gatecost diff` | In a git repository, compares the working tree (staged and unstaged edits, and untracked RTL files) with `HEAD`. Outside git, uses the most recent snapshot; otherwise fails with `NO_BASELINE`. |

## 8. Command-Line Interface

The complete reference for commands, options, the `estimate` notation, and the configuration file is [`docs/CLI.md`](CLI.md) (normative). Summary:

```
gatecost diff      [PATH ...]            # cost delta (see §7 for baselines)
gatecost cost      [PATH ...]            # absolute cost of a design
gatecost estimate  "<expression>"        # cost of a hypothetical construct
gatecost estimate  --rtl "<fragment>"    # cost of an RTL fragment
gatecost estimate  --compare A B         # compare alternatives
gatecost snapshot                        # record the current state as a baseline
gatecost init                            # write a gatecost.toml from detected values
gatecost profiles [show NAME]            # list or show cost profiles
gatecost clean                           # remove caches and snapshots
gatecost validate-output FILE            # validate a JSON result against the schema
```

Common options: `--top`, `--profile`, `--format {agent,json,text,markdown}`, `--define`, `--incdir`, `--filelist`, `--budget`, `--fail-on-increase`, `--max-lines`, `--no-cache`.

### 8.1 Agent output format

The `agent` format is line-oriented, pure ASCII, and bounded in size (about 400 tokens by default). The first line always states the delta, its range, the verdict, and the confidence; contributor lines follow, sorted by absolute delta and attributed to `file:line` with a reason; `WHY`, `WARN`, and `ASSUMED` lines convey how far the figure can be trusted. Example:

```
DELTA +342 GE (+281..+410) +1.2% verdict=INCREASE confidence=medium
TOP top_core before=28410 after=28752
+210 alu.sv:87 added MUL 16x16
+96 alu.sv:102 width MUX 4:1 w16->w32
+36 regfile.sv:41 added DFF x36 (register stage)
OTHERS 2 net=0
WHY medium: delta range is -18%/+20% of the estimate
```

The grammar, the formats of the other commands, the verbosity options, and the interpretation guide for agents are specified in `docs/OUTPUT.md`.

### 8.2 `estimate`

`estimate` costs a standalone construct, either in a compact notation (`mul 32x32`, `mux 8:1 w64`, `reg 128 sync_reset enable`, sums such as `mul 16x16 + add 32`) or as an RTL fragment in Verilog/SystemVerilog or VHDL with inferred inputs and outputs. `--compare` evaluates several alternatives and reports the cheapest and whether their ranges overlap. This lets an agent weigh design options before writing code. The notation and the fragment semantics are specified in `docs/CLI.md` §3.

### 8.3 Exit codes

| Code | Meaning |
|------|---------|
| 0 | Success |
| 1 | Budget exceeded (`--budget`, `--fail-on-increase`); the normal result is still printed |
| 2 | Usage or configuration error |
| 3 | Analysis could not produce a result (no usable sources) |

Partial results (unsupported constructs) exit with 0; the condition is conveyed in the output and the `confidence` field.

## 9. Output Contract (JSON)

The JSON output is a single envelope `{schema_version, tool, command, status, profile, config, result, diagnostics, meta}` whose `result` has a documented shape per command (`diff`, `cost`, `estimate`). A JSON Schema is shipped with the package and validated in the test suite. Field-level definitions are in `docs/OUTPUT.md` §3. Fields are added without changing `schema_version`; the version changes only when an existing field is removed or altered. Consumers must ignore unknown keys.

### 9.1 Confidence levels

Confidence is derived from the relative range `r = (Δ_max − Δ_min) / (2·max(|Δ_typ|, 20 GE))`, which is also reported in the JSON output, from the composition of the change, and from the profile. Definitions are in `docs/COST_MODEL.md` §5.2.

| Level | Meaning |
|-------|---------|
| `high` | No unsupported construct in the changed cone, at least 90% of the delta in well-modelled classes, `r ≤ 0.2`. |
| `medium` | No unsupported construct in the changed cone and `r ≤ 0.5`. |
| `low` | Anything else: unsupported constructs, unknown black boxes, macros without a table, or more than 30% of the delta in poorly modelled classes. |

## 10. Configuration

An optional `gatecost.toml` at the project root:

```toml
[project]
top = "top_core"
sources = ["rtl/**/*.sv"]
filelists = ["rtl/files.f"]
incdirs = ["rtl/include"]
defines = { SYNTHESIS = "1", WIDTH = "32" }

[project.libraries]            # VHDL library mapping (default: everything in "work")
core = ["rtl/core/*.vhd"]

[project.architectures]        # VHDL architecture selection when an entity has several
cpu = "rtl"

[cost]
profile = "generic-asic"

[budget]
max_ge = 50000
max_delta_ge = 500

[report]
max_lines = 10
threshold_ge = 5
```

Command-line options override the project file.

## 11. Agent Integration and Distribution

The repository **is** the agent skill. A project adopts it with `git submodule add <url> <skills-dir>/gatecost`, where `<skills-dir>` is whichever skills directory its agent toolchain reads. The complete distribution model is specified in [`docs/DISTRIBUTION.md`](DISTRIBUTION.md); its main points are:

- `SKILL.md` sits at the repository root, with a minimal portable frontmatter (`name`, `description`) and a short body (under about 120 lines) that tells the agent when to use the tool, which command fits which situation, how to read the output, how to word the answer to the user (always with the range and the confidence), and how to react to common errors.
- A launcher, `scripts/gatecost`, runs the tool from any mount path with no installation: it locates the sources relative to itself and uses only the Python standard library.
- The tool never writes inside its own directory. Bytecode goes to the user cache directory; snapshots and the analysis cache go to `<project>/.gatecost/`, which carries its own `.gitignore`, or to the user cache. The submodule therefore stays clean, and the host project's `git status` is unaffected.
- The tool analyzes the host project: discovery starts at the working directory and excludes the skill directory itself.
- A `pip install` path (`pyproject.toml`) also exists for non-agent use; it provides the same `gatecost` command.

## 12. Performance and Caching

- Targets on a modern laptop: a cold analysis of a design of roughly 100k lines of RTL in a few seconds; a warm `diff` of a single-module change in well under one second (under 300 ms for a design of that size); a small design in under 300 ms cold.
- Parsing and elaboration results are cached on disk, keyed by a hash of file contents, defines, and include contents. The cache lives in `<project>/.gatecost/` or in the user cache directory, never in the tool's own directory. It is purely an optimization: removing it, or running with `--no-cache`, never changes results.
- Start-up: under 300 ms cold and 100 ms warm for a small design, with lazy imports and a shared bytecode cache.
- Analysis is restricted to the cone of the changed files when the baseline is a snapshot or git reference, then expanded only as far as hierarchy and parameters require.
- Cache entries are JSON.  A cost tree is stored as a small entry (one header per module with its name, canonical hash, instance edges, diagnostics and cost sums) plus a content-checked *operations pack* (`.gcp`) holding the operations of the modules written by that analysis; entries of later analyses refer to the packs of the modules they share, and a reader fetches the operations of a module only when it looks at them (the differ looks only at modules whose canonical hash or instance count changed).  A tree whose pack is missing or damaged is a miss.
- A full analysis of a Verilog/SystemVerilog project also stores a per-file index (the modules each file defines and the module names they instantiate, whether the file must always be read, its `ifdef` names and its parse diagnostics).  The changed-cone analysis then parses only the changed files, the files that must always be read, the ancestors of the changed modules and the direct children of those, and takes everything else from the index and the baseline tree; it falls back to reading every file when a module is defined twice, when the root set would change, or when any file is not plain Verilog/SystemVerilog.
- Measured status and the numbers still above target are in `FRONTEND.md` section 8.

## 13. Determinism and Robustness

- Identical inputs and profile always produce byte-identical output, including ordering.
- The tool never executes any code from the analyzed sources and never opens network connections.
- Malformed or hostile input must not cause crashes, unbounded memory use, or unbounded run time: expansion and unrolling are bounded by configurable limits, and reaching a limit yields a diagnostic.

## 14. Validation and Testing

- **Unit tests** per stage: lexer, parser, preprocessor, elaborator, each cost formula, differ matching.
- **Golden tests**: a corpus of small RTL fixtures with expected IR and cost trees.
- **Property tests**: reformatting and renaming do not change the cost; moving code between files does not change the cost; adding an unused module does not change the top cost.
- **Differ tests**: pairs of before/after fixtures with expected contributors and deltas, including refactors that must yield a zero delta.
- **Reference validation** (maintainers only, not a user requirement, not part of CI): `scripts/calibration_bench.py` compares estimates with the areas of a real synthesis (Yosys + Nangate 45 nm, `scripts/yosys_area.py`) on generated micro-benchmarks, repository examples and corpus designs, and `tests/reference/yosys_nangate45.csv` freezes those areas so that `tests/test_calibration_reference.py` and `--frozen` runs need no Yosys. It was used to tune the built-in profile defaults; the confidence rules in §9.1 are not tuned yet. Results and limits: `COST_MODEL.md` §5.3. `scripts/validate_reference.py` compares with arbitrary area reports.
- **Agent acceptance tests**: scripted end-to-end scenarios (edit, query, parse output) verifying that the `agent` and `json` outputs remain parseable and complete.
- The test suite itself uses only the standard library (`unittest`).

## 16. Design Decisions and Extension Points

Decisions taken:

1. Module-level deltas are reported per instance with the instance count shown separately, and as intrinsic and multiplicity components (`DIFF.md` §4).
2. The built-in profile assumes moderate timing and `mux`-style enables (`COST_MODEL.md` §7); other styles are selected by policy keys.
3. The tool needs no calibration or reference data from its users. Maintainers may compare estimates with real synthesis reports to tune the built-in defaults (§14).

Extension points (not required for the tool to work; added when needed):

- Additional built-in profiles for other cost targets, for example FPGA primitive counts (LUT, FF, DSP, BRAM); the profile format and the primitive-based formulas allow it.
- Additional front-ends: the IR is language-neutral (`IR.md`).
