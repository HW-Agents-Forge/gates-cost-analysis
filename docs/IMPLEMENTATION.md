# gatecost — Implementation Plan

Status: Draft. This document sequences the construction of the tool described in `SPEC.md`. It defines no behavior of its own: every behavior is specified in the referenced documents.

The project is built incrementally. Each stage below delivers something an agent can already use, ends with an explicit acceptance check, and leaves the repository in a releasable state. A stage may begin when the stages it depends on are accepted; stages without a dependency between them can proceed in parallel.

## 1. Engineering Conventions

- **Language level:** Python 3.11, standard library only (`SPEC.md` §15). A lint test rejects third-party imports and features newer than 3.11.
- **Layout:** as in `DISTRIBUTION.md` §2. One package `gatecost` under `src/`; sub-packages `frontend/{common,verilog,vhdl}`, `elab`, `ir`, `cost`, `diff`, `report`, `cli`, `profiles`.
- **Purity:** every pipeline stage is a function from immutable inputs to immutable outputs; I/O (files, git, cache) is confined to `cli` and a small `io` layer, so every stage is testable without a file system.
- **Data classes:** `dataclass(slots=True, frozen=True)` for IR and AST nodes where mutation is not needed; builders are the only mutators.
- **Typing:** full type annotations; `mypy --strict` runs in CI as an optional check (not a runtime dependency).
- **Tests:** `unittest` only. Fixtures live under `tests/fixtures/` (RTL pairs and expected outputs). Golden files are regenerated by an explicit script, never automatically.
- **Determinism:** no reliance on dictionary order for output, no `hash()`, no timestamps (`IR.md` §7, `OUTPUT.md` §1).
- **Error handling:** front-end and analysis code reports problems as diagnostics, never by raising across stage boundaries; only the CLI converts unexpected exceptions into `ERROR INTERNAL` (`OUTPUT.md` §6).
- **Continuous integration:** the full test suite on Python 3.11 and on the latest release, on Linux and macOS; the launcher tests on a path with spaces; the start-up benchmark.
- **Review gates:** each stage's pull request includes the tests listed in the corresponding specification sections and updates the documents if behavior had to change.

## 2. Stages

### Stage 1 — Skeleton, launcher, command line, output plumbing

**Deliver:** repository layout; `scripts/gatecost` with the Python version check and `sys.pycache_prefix` handling; the argument parser for every command and option of `CLI.md`; configuration loading (`gatecost.toml`, environment, precedence); the result-object model and the `agent`, `json`, `text`, `markdown` renderers fed by hand-built results; error codes and exit codes; `VERSION`; `SKILL.md` and `README.md`; the JSON Schema and `validate-output`; project-root detection and source discovery with exclusions; the `clean` and `init` commands; `help`.

**Unimplemented analysis commands** return a well-formed `ERROR NOT_IMPLEMENTED` (exit 3) so the skill file can already be checked against the parser.

**Spec references:** `CLI.md`, `OUTPUT.md`, `DISTRIBUTION.md` §§3–6.

**Accepted when:** every command example in the documents parses; renderers reproduce the golden outputs of `OUTPUT.md` §7 from hand-built results; the launcher runs identically from the three mount paths; a full workflow leaves the skill directory clean.

### Stage 2 — Cost model and `estimate`

**Deliver:** the primitive table and the `generic-asic` profile; profile loading with `extends` and overrides; every formula of `COST_MODEL.md` §3 in the three scenarios; integer milli-GE arithmetic; quality classes and the confidence derivation; scenario-wise delta arithmetic; the compact `estimate` notation including sums, multipliers, constants, and `--compare`; `profiles` and `profiles show`.

**This is the first stage usable by an agent:** it answers "what would a 32x32 multiplier cost here?" without any HDL parsing.

**Depends on:** stage 1. **Spec references:** `COST_MODEL.md`, `CLI.md` §3.1, §3.3.

**Accepted when:** all exact-value, constant-handling, and property tests of `COST_MODEL.md` §7 pass for the operations that do not need the IR (the width- and sharing-dependent ones move to stage 4); the sanity bands hold; `estimate` output matches the documented examples.

### Stage 3 — IR, builder, and analysis passes

**Deliver:** nets, `SigSpec`, nodes, and the operation catalogue of `IR.md` §§2–3; the builder with hash-consing, constant folding, and the identity table (`IR.md` §4); the known-bits, dead-logic, demanded-bits, effective-width, fusion, and sharing passes (`IR.md` §6); keys and canonical hashes (`IR.md` §7); the textual dump; the cost tree built from an IR; the reductions of `COST_MODEL.md` §4 applied through the passes; hierarchy and instance counts.

**Exposed through the Python API** (`analyze_ir`, `cost_tree`) and tested with IR constructed by hand or by a small test-only DSL; no HDL is parsed yet.

**Depends on:** stage 2. **Spec references:** `IR.md`, `COST_MODEL.md` §4.

**Accepted when:** all builder, pass, key, determinism, and invariant tests of `IR.md` §12 pass, and the width-, sharing-, and fusion-dependent cost tests of `COST_MODEL.md` §7 pass on hand-built IR.

### Stage 4 — Verilog front-end (core) and `cost`

**Deliver:** reader and preprocessor with the line map; lexer; parser with error recovery for modules, ports, parameters, nets, `assign`, `always` blocks, `if`/`case`, and the expression grammar; the elaborator for parameters, constant expressions, width and signedness inference, hierarchy, and procedural lowering to IR (`FRONTEND.md` §2, §3 core rows); diagnostics and the unresolved-information defaults (`FRONTEND.md` §4, §6); the `cost` command end to end; `estimate --rtl` for Verilog fragments.

**Depends on:** stage 3. **Spec references:** `FRONTEND.md` §§1–4, §6–7, §9.

**Accepted when:** the lexer, preprocessor, parser, and elaborator tests of `FRONTEND.md` §9 pass for the covered constructs; error-recovery fixtures leave neighbouring code analyzed; `gatecost cost` on a small multi-module Verilog design reports plausible module-level totals within the sanity bands.

### Stage 5 — Differ, baselines, and `diff`

**Deliver:** the matching tiers, multiplicity decomposition, reasons, cause tracing, views, and verdicts of `DIFF.md`; baseline resolution (git reference, snapshot, two directories, default to `HEAD`) and the `snapshot` command; the changed-module scope and the module-level cost cache with canonical-hash short-circuit; the `diff` command with all output formats; budgets and exit code 1.

**This stage completes the agent loop** (edit, ask, read the explanation) for Verilog designs.

**Depends on:** stage 4. **Spec references:** `DIFF.md`, `DISTRIBUTION.md` §4.1, `FRONTEND.md` §5.

**Accepted when:** all zero-delta, additivity, symmetry, transitivity, matching, multiplicity, reason, and verdict tests of `DIFF.md` §12 pass; results with and without the cache are identical; the agent acceptance scenarios (edit, `diff`, parse the output) pass.

### Stage 6 — Verilog and SystemVerilog completeness

**Deliver:** `generate`, functions and tasks, packages, `typedef`/`enum`/packed `struct`, unpacked arrays and memory inference, interfaces and modports, gate primitives, casting and streaming operators, `casez`/`casex`, latch and enable recognition refinements, tri-state approximation, `defparam`, skipped-region handling, and every limit of `FRONTEND.md` §7.

**Depends on:** stage 5 (so that each feature is tested through `diff` as well as `cost`). Can proceed in parallel with stage 7.

**Accepted when:** each row of the Verilog/SystemVerilog support matrix (`FRONTEND.md` §3) has at least one passing fixture at its documented level, and the robustness fuzz test terminates cleanly on all mutated fixtures.

### Stage 7 — VHDL front-end

**Deliver:** the VHDL lexer and parser with error recovery; library and unit resolution; the built-in IEEE package model; the lightweight type checker for operator and conversion resolution; process lowering (clocked, combinational, resets, enables); `generate`; enumeration encoding; records; mixed-language instantiation; `estimate --rtl --lang vhdl`.

**Depends on:** stage 4 (shares the IR, the symbolic executor, and the elaboration infrastructure). Can proceed in parallel with stage 6.

**Spec references:** `FRONTEND.md` §10.

**Accepted when:** the VHDL parser, elaborator, and width-rule tests pass; the paired Verilog/VHDL corpus yields identical IR dumps after name normalization and equal costs; mixed-language fixtures pass in both directions.

### Stage 8 — Performance and incremental analysis

**Deliver:** the on-disk parse and cost caches with their invalidation rules; lazy per-command imports; profile parsing on demand; the changed-cone analysis for large hierarchies; profiling-driven optimization of the lexer and the builder.

**Depends on:** stages 5 and 7 (so that both languages are measured).

**Accepted when:** the benchmark suite meets the targets of `SPEC.md` §12 and `FRONTEND.md` §8 on generated designs of 10k and 100k lines, and the cache tests produce identical results with and without the cache.

### Stage 9 — Hardening and release readiness

**Deliver:** the large fixture corpus and the fuzzing campaigns; the optional real-world smoke tests with their coverage report; the maintainers' reference validation (`SPEC.md` §14: `scripts/validate_reference.py`, and the Yosys + Nangate 45 calibration bench `scripts/calibration_bench.py` with its frozen reference) and the tuning of the profile defaults and confidence thresholds from it; the trigger-prompt test set for `SKILL.md`; final `README.md` with adoption and permission snippets for the three agent toolchains; license decision and files; tagged release.

**Depends on:** all previous stages.

**Accepted when:** the complete test suite is green on both interpreters and both operating systems; the documented examples of every document run unchanged; a clean-room trial in a sample project adds the repository as a submodule in each of the three skills directories and completes the three agent workflows of `DISTRIBUTION.md` §7.

## 4. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Estimates are too far from real synthesis results, eroding trust | High | Scenario ranges and confidence levels (`COST_MODEL.md` §5); the maintainers' reference-validation script and tuning in stage 9; conservative defaults where the model is weakest (dividers, memories); explicit guidance to the agent in `SKILL.md`. |
| SystemVerilog is large, and real designs use constructs outside the supported subset | High | The degradation ladder (`FRONTEND.md` §1) keeps results partial rather than failing; stage 6 is driven by a corpus of real designs; diagnostics report what was skipped so that gaps are measurable. |
| VHDL operator and overload resolution is complex | Medium | A lightweight type checker restricted to the standard packages' API; `UNRESOLVED_OVERLOAD` as a visible fallback; the paired-corpus equivalence test as a regression net. |
| Python parsing speed on large designs | Medium | Regex-driven lexer, linear-time passes, caches, and the changed-cone scope; benchmarked in stage 8 with a defined budget. |
| Spurious deltas from unstable matching | Medium | The zero-delta, symmetry, and transitivity invariants are tests from stage 5 onward (`DIFF.md` §12). |
| Documentation drifting from the tool | Medium | Tests that parse every documented command and compare golden outputs; stage reviews update documents with code. |
| A skill that executes repository code in the host project is a trust risk | Medium | No network, no execution of analyzed sources, writes only to documented locations (`DISTRIBUTION.md` §8); adopters pin to reviewed commits. |

## 5. Definition of Done (every stage)

1. The behavior matches the referenced specification sections, or the specification was updated in the same change with the reason stated.
2. All tests listed in the referenced sections pass, plus regression tests for every defect found during the stage.
3. The full suite passes on both interpreters; the start-up benchmark still meets its budget.
4. `SKILL.md`, `README.md`, and the documents are consistent with what the tool does (the documentation-sync tests pass).
5. No new dependency, no write outside the documented locations.
